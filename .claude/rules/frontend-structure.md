# Front-end source structure

Organize `apps/frontend/src` by **domain**, as vertical module slices, the same way the backend has one `internal/<domain>` package per domain. Code that belongs to one domain lives in that domain's folder. The only top-level `components/`, `hooks/` and `lib/` folders are the [shared layer](#shared-layer), which holds domain-agnostic code.

Each domain gets one folder named after it (plural, matching the backend route: `applications`, `organizations`, `projects`, ...). Example for the application domain:

```
src/applications/
  layout/                  # main layout applied to all application sub-routes
  data/                    # custom hooks: the only way UI reads or modifies application data
    api/
      client.ts            # individual fetch HTTP methods for this domain's endpoints
      queries/             # TanStack Query wrappers (useQuery, query keys/options)
      mutations/           # TanStack Query wrappers (useMutation, cache invalidation)
  components/<name>/<name>.tsx   # small shared components that together build the pages/menus
```

## Rules

- **`data/`** hooks hide how data is retrieved or modified. Components and routes call these hooks (e.g. `useApplication(id)`, `useDeployApplication()`). They never call `client.ts`, `fetch` or TanStack Query directly.
- **`data/api/client.ts`** holds only the plain HTTP calls for the domain, one function per endpoint. It is built on the shared request/`ApiError` core in `src/api`, which owns URLs, cookies and the response envelope. It has no React and no caching.
- **`data/api/queries` and `data/api/mutations`** are the only places that touch TanStack Query for the domain. They own query keys, and mutations invalidate the related queries.
- **`components/<name>/<name>.tsx`**: one folder per component. Keep components minimal and composable, with the page assembled from them.
- **`layout/`** is the domain's shell, shared by all its sub-routes.
- **Routes** stay in `src/routes` because TanStack Router uses file-based routing. Keep route files thin: wire params, the domain's `layout` and its components, and put no data fetching or business logic there.
- A domain must not import another domain's internals. If something is needed across domains, move it to the [shared layer](#shared-layer) instead of reaching in.

## Shared layer

Global code that no single domain owns lives at the top of `src`:

```
src/
  api/                           # request/ApiError core: URLs, cookies, response envelope
  components/ui/                 # shadcn primitives (button, input, card, ...), managed by the shadcn CLI
  components/<name>/<name>.tsx   # shared composite components (e.g. form fields, empty states)
  hooks/                         # shared hooks with no domain data (e.g. useDebounce, useMediaQuery)
  lib/                           # shared helpers (e.g. shadcn's `cn` in lib/utils.ts)
```

- Shared code must be **domain-agnostic**: it never imports from a domain folder and never knows about a domain's data or endpoints. Domains import from the shared layer, never the other way round.
- Start new code in its domain. Move it to the shared layer only once a second domain needs it, or when it has no domain at all (UI primitives, generic utilities).
- Hooks that read or modify a domain's data stay in that domain's `data/`, never in `src/hooks`.
- `components/ui/` is generated by `pnpm dlx shadcn@latest add <component>`. Keep the CLI's layout there: flat `<name>.tsx` files, not the `<name>/<name>.tsx` folders used elsewhere.
- Third-party blocks that bring their own feature logic (e.g. Supabase auth forms) are not primitives. Move them into the owning domain (e.g. `src/auth/components/...`) after installing them.
